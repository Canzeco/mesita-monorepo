# apps/web-admin — internal admin console

> Read root [`CLAUDE.md`](../../CLAUDE.md) first; Notion holds the deep docs. Package rules only below.

- Light theme + semantic tokens; calm, dense, unornamented. Design map: Notion Docs › Design. New UI takes chrome from [`src/components/admin-ui/`](./src/components/admin-ui/), never a route-local shim. `/brand` is read-only, out of the sidebar.
- Clients never touch the DB — everything via `admin-web-*` Edge Functions. The EF-invoke wrapper is the deliberate **`Result` variant** (consumer/business throw `EFError`) — keep it.
- Every config page: server seeds → client form → **WHOLE-BLOB save** to one `app_config` column, normalizer in lockstep, `dirty` gated on `loadError`. A knob nothing reads is **STAGED**.
- **A label never repeats its section heading** — Configurations › **Intake**, never "Intaker Config"; tabs too. Labels live in each route's `nav.ts` and **a rename stops there**: routes, blobs, EF names never follow. **Sidebar in product-flow order**; the set is code-defined in `CONFIGURATIONS_NAV`. **Intake** = sourcing's gate (families, floors, **one Where** copied onto every channel) + the Intaker (**12 subfunctions**, listed once: Create is **one run**, Enrich is **sequential runs**); `/sourcing-config` redirects. No Atlas page (spec: Docs › Atlas). **Verification** = PLACE ownership proof, **Ojo** = reading a guest's screenshot. **Memo is not a row** — it IS the chat engine, so it belongs to Discovery; it has no editor and runs on in-code defaults.
- **Discovery** (`/filters-config`) is TWO BOXES: Signals · Engines. Each signal is a function; each engine is `Engine(signal(),…)`. Signals is ONE table — Input · Process · Output · every hyperparameter including the exponent. **Each function names its vendor APIs in bold** (None at rank time for every signal). **Promoting is not a signal**. Only a **wired** engine gets a param (Swipe `ranked`). Slotting and filters persist on the blob with **no knobs**. Blob `app_config.discovery_config`.
- **Visits** (`/visits-config`): Bill · Sync · Report (`visits_config`) plus **Ojo** (`ojo_config`, own Save). Unwired visits keys stay in that blob, off the HTML. **Orders Config** = the REMOTE context. Neither prices anything — rates are Promos. Premium clamps up to the Free quota; the preselected tip must be a chip that exists.
- **Promos Config** (`/rewards-config`, **one page**) edits COMPONENTS; storage keeps the GRID: `standing = base + classStep + planStep`. **THREE visit boxes** (one per paid strategy) — knobs first, stacking behind a disclosure — then **Orders Promos Soon** (no knobs, blob grid kept), one Save, then the visit-spread simulator (assumptions only; follows live knobs). `/rewards-config/tiers` and `/distribution` redirect here. `additivityError` REFUSES a grid the components can't express or whose class offsets decrease; only `google-vs-story` warns. Twin: `web-business/lib/business/promos.ts`.
- `database.types.ts` is hand-copied across the web apps — regenerate from cloud, never hand-edit. CI `web-admin.yml`: lint · typecheck · build, Node 22+, path-filtered.
